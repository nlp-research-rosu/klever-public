## 4. Adequacy and real-program pinning

### Plain-language claims

`PILE-PREFIX-SPEC` says: for mathematical integer `N > 0`, start in the
ordinary module configuration, load the one-function module, and call
`make_a_pile(N)`. Fixed semantics must reach the real while-loop head after
allocating heap list 0, binding `n=N`, `stones=ref(0)`, and `i=0`, and pushing
the exact call frame. This is an initialization/prefix claim, not the final
result claim.

`PILE-LOOP-SPEC` says: for `N > 0` and `0 <= I <= N`, if the current local
bindings are `n=N`, `stones=ref(0)`, `i=I` and heap list 0 initially contains
arbitrary prefix `VS`, then executing the real while loop, the following
`return stones`, and `#endcall` returns `ref(0)`, pops the frame, and leaves
heap list 0 equal to `VS ++ pile(N,I)`. Here:

`pile(N,I) = [N+2*I, N+2*(I+1), ..., N+2*(N-1)]`.

The prefix post-state is exactly a loop pre-state with `I=0` and
`VS=.ValSeq`; all cells, frame, heap locations, and side conditions match.
Reachability transitivity therefore yields an entry-to-result theorem:
`ref(0)` points to `pile(N,0)`, the intended list. The result is not a free
variable or implication-only condition: both the returned reference and its
heap contents are constrained.

The focused assessment
[05_local_extension_assessment.md](evidence/05_local_extension_assessment.md)
accounts for every candidate-local directive. Its conclusions are:

- `pileCondition`, `pileLoopBody`, `pileBody`, `pileClosure`, and `pileModule`
  are exact macro abbreviations. They add no execution rule and skip no body.
- `pile` is a pure definitional result summary, not an operational bridge. Its
  guards `I>=N` and `I<N` are disjoint and exhaustive over integers. The
  recursive case increments `I`, so it descends in `N-I` until the base case.
- `valSeqConcat(VS,.ValSeq)=VS` and concatenation associativity are true
  equations of the supplied recursive list concatenation, by induction.
- There are no candidate priority rules, ordinary operational semantic rules,
  opaque/no-evaluator symbols, unconstrained oracles, or proof-local helper
  claims.

## 6. Fresh non-vacuity test

The reviewer mutation in
[06_spec_vacuity.k](evidence/06_spec_vacuity.k) changes the result-constraining
heap obligation from `VS ++ pile(N,I)` to `VS ++ pile(N,I+1)`, thereby omitting
the first remaining level when `I<N`.

The mutation is demonstrably false at satisfying witness
`N=1, I=0, VS=.ValSeq`: actual execution appends `1`, whereas the mutant target
requires `pile(1,1)=.ValSeq`.

The dry run compiled the mutated claim successfully and exited 0
([06a_vacuity_dry_run.log](evidence/06a_vacuity_dry_run.log)). The actual proof
exited 1 with `WarnStuckClaimState`. Its residual explicitly contrasts
`VS ++ pile(N,I+1)` with
`VS ++ [N+2*I] ++ pile(N,I+2)` under `I<N`; this is the expected unmet result
obligation, not a parser error, missing import, timeout, or unrelated crash
([06b_vacuity_kprove.log](evidence/06b_vacuity_kprove.log)). The exact runner is
[06_run_vacuity.sh](evidence/06_run_vacuity.sh).

Stage result: pass; the proof is non-vacuous and result-sensitive.
