## 2. Program fidelity and candidate-versus-canonical checks

The trusted contract in `/reference/prompt.py` is: for a finite `List[int]`
and an integer `delimeter`, return a new list with exactly one delimiter
between each consecutive pair. The empty input returns `[]`; a singleton is
unchanged; there is no leading or trailing delimiter. The contract states no
length or integer-magnitude bound.

The canonical program handles the empty case, appends each non-final number
and delimiter, then appends the final number. The candidate instead iterates
all elements and appends a delimiter whenever its output accumulator is
already nonempty. Those algorithms are extensionally equivalent: after the
first iteration the accumulator is nonempty regardless of the first integer's
truth value.

Using the copied trusted translator, the command

```text

  /tmp/audit-work/5-intersperse/solution.py
```

exited 0 and generated bytes identical to the submitted `solution.mpy`
(SHA-256 `280eebaf...3d413d`).

The independent script `evidence/02_differential.py` imports both the trusted
canonical entry point and the candidate entry point and also computes a
separately written direct-list oracle. It checks the documented examples,
empty/singleton/two-element branch boundaries, zero/negative/duplicate/very
large integers, an exhaustive Cartesian sample of lengths 0 through 5 over
five values and five delimiters, and 2,000 deterministic generated lists of
lengths 0 through 40. `bash evidence/02_fidelity.sh` exited 0:


The script, complete input generator, oracle, command, and result are in

**Stage 2 result: PASS.** The submitted implementation is faithful on the

## 4. Adequacy and real-program pinning

### Plain-language claims

1. **Empty loop claim (`spec.k:7`).** If the loop iterator is empty, the
   accumulator heap object is empty, and the named frame/heap keys are fresh
   from their framed maps, the loop terminates without changing the shown
   state.
2. **First-iteration claim (`spec.k:33`).** Starting with a nonempty iterator
   and an empty result object, the loop consumes every iterator element,
   changes the result heap object to
   `intersperseAcc(.ValSeq, vCons(V,REST),D)`, and binds `number` to the last
   consumed element.
3. **Steady-state claim (`spec.k:70`).** Starting with a nonempty accumulator,
   the remaining iterator appends `D` and each remaining element, producing
   `intersperseAcc(existing,REST,D)` and the correct final `number` binding.
4. **Entry claim (`spec.k:106`).** From the standard module configuration,
   load the submitted module and call its exact `intersperse` closure on an
   arbitrary finite `ValSeq` and arbitrary K integer `D`. It returns fresh
   `ref(0)`; heap 0 contains `intersperseVS(NUMBERS,D)`; the callee frame is
   gone; allocation counters, module binding, stack, return state, exception,
   and exit code all have their stated final values.

All preconditions are satisfiable. For the helper claims, take `L=1`, `H=0`,
`SCOPES=.Map`, `HEAP=.Map`, `PARENT=root`, `CONT=.K`, and `D=4`; use an empty
iterator for claim 1, `V=1, REST=vCons(2,.ValSeq)` for claim 2, and additionally
`OLD=1, A=1, AS=.ValSeq` for claim 3. The freshness guards then reduce to true.
For the entry claim, `NUMBERS=vCons(1,vCons(2,vCons(3,.ValSeq)))` and `D=4`
satisfy its sort-enforced precondition.

### Mechanical pinning and concrete substitution

Trusted retransliteration already pins `solution.py` to `solution.mpy`. The
reviewer then extracted the `Module(...)` inside the entry claim's `#loadAll`,
normalized only the K spelling of empty list units (`.Exprs`/`.Stmts`) to the
standalone MPY spelling (omission), and parsed both terms with `kast --output
kore`. The normalized KORE files are byte-identical with SHA-256
`9d31aa20...52815a`; see `evidence/04_kast_solution.log`,
`evidence/04_kast_entry_module.log`, and
`evidence/04_extract_entry_module.py`. Thus the claim executes the same
function name, parameters, binding, and body—not a substitute.

For `numbers=[1,2,3]` and `D=4`, both Python implementations and the claimed
heap list are `[1,4,2,4,3]`. The finite, bridge-free ground entry claim in
`evidence/04_ground_spec.k` unrolls the exact program without helper
circularities; its `kprove` exited 0 with exact `#Top`
(`evidence/04_kprove_ground.log`).

The output is not free or tautological. It is fixed by the complete,
terminating equations for `intersperseVS`/`intersperseAcc`, and the claim fixes
the returned reference and exact heap content. A material body-sensitivity
mutation changed both occurrences of the executed closure body so later
iterations append `Int(99)` while retaining the original result obligation.
It did not merely edit external Python. The mutation parsed, reached the final
state, and `kprove` exited 1 with a stuck residual containing `D != 99` and the
actual heap `[V,99,V0]`; see `evidence/04_body_mutation.k` and
`evidence/04_kprove_body_mutation.log`.

The use of bare `list(NUMBERS)` for the input is a sound representation for
this function: the fixed semantics explicitly admits read-only bare input
lists, and the body iterates but never mutates or aliases `numbers`. The output
is separately allocated and fully modeled.

**Stage 4 result: PASS.** The entry theorem is satisfiable,
result-constraining, body-sensitive, and mechanically pinned to the submitted
program.

## 7. Proven versus assumed accounting

### What is formally established

Under the freshly built supplied K semantics and the six truthful
proof-local equations, for every finite K `ValSeq NUMBERS` and every K integer
`D`, execution from the entry claim's standard configuration of the exact
translated module and exact call reaches a normal final state returning
`ref(0)`. Heap 0 equals the recursively defined sequence that preserves each
input element and inserts exactly one `D` between consecutive elements. The
callee scope is removed, the module closure remains exact, the stack and
return state are clear, allocation counters are correct, there is no
exception, and exit code is 0.

The theorem is actually broader in element type than required: `NUMBERS` may
contain arbitrary `Val` elements, while the HumanEval contract asks only for
integers. It is not length-bounded or example-bounded and does not narrow the
source domain.

### Trust ledger and evidence

- **K toolchain and built-in theories.** The reachability engine and the
  imported K `INT`, `BOOL`, `STRING`, `MAP`, `LIST`, and `K-EQUAL` theories are
  trusted primitives. The reconstructed K 7.1.293 result, ground theorem,
  body mutation, and false postcondition give independent positive and
  negative sensitivity evidence.
- **Supplied semantics.** The fixed source tree is the launcher-selected trust
  boundary. Its integrity is exact, and every relevant rule was statically
  checked. No opaque supplied symbol is a theorem dependency.
- **Translator bridge.** The trusted CPython-AST translator is not proved
  correct inside K. Here its output is byte-reproducible, the source uses a
  small supported subset, and parser-normalized KORE identity mechanically
  connects that output to the entry claim.
- **Input representation bridge.** Python's read-only input list is represented
  by bare `list(NUMBERS)` in the claim. This relies on the supplied semantics'
  stated bare-input convention and on the inspected fact that the body does
  not mutate or retain the input.
- **Intent bridge.** The natural-language phrase "insert between consecutive
  elements" is interpreted by the transparent structural equations for
  `intersperseAcc`. This is an ordinary mathematical reading, not an opaque
  oracle. The ground theorem and 21,539-case differential test support the
  bridge, but finite testing is not used in place of the universal K proof.
- **Empirical checks.** The Python differential run supports
  candidate-versus-canonical fidelity on its documented finite sample. The
  seven-case LLVM run supports concrete execution of the relevant semantics.
  Neither is presented as a universal theorem.

The result is a partial-correctness statement at the requested level. It does
not claim behavior for inputs outside the `List[int], int` contract, Python
resource exhaustion, or constructs omitted by the supplied partial language.
Those exclusions do not remove any material source-contract input.

Gate A (real-program soundness), Gate B (intent adequacy), and Gate C (trust
and auditability) all pass. There is no material adequacy gap and no
non-fatal limitation that warrants downgrading a legitimate proof.
