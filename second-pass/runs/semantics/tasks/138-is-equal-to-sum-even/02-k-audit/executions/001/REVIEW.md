## 2. Program fidelity and candidate-versus-canonical checks

### Contract and implementation

The trusted prompt asks whether integer-like input `n` can be expressed as the
sum of exactly four positive even integers and gives `4 -> False`, `6 -> False`,
and `8 -> True`. The trusted canonical implementation returns:

```python
n % 2 == 0 and n >= 8
```

The submitted implementation returns:

```python
n >= 8 and n % 2 == 0
```

For mathematical integers these differ only in short-circuit order and are
extensionally equal. The proof's formal domain is K `Int`, so it does not claim
behavior for floats, strings, or other Python objects. It is stronger than any
positive-integer restriction because it covers every mathematical integer.

## 4. Adequacy and real-program pinning

### Claims in plain language

All four claims start from the same realizable state: environment location 0,
an empty module scope whose parent is the supplied builtins scope, allocation
locations 1 and 0, empty heap and stack, no pending return or exception, and
exit code 0.

1. Universal claim: for every mathematical integer `N`, the returned Boolean
   equals `N >= 8 and pyMod(N, 2) == 0`.
2. True corollary: when `N >= 8` and its remainder modulo 2 is zero, return
   `true`.
3. Low corollary: when `N < 8`, return `false`.
4. Odd/nonzero-remainder corollary: when `N >= 8` and its remainder modulo 2 is
   nonzero, return `false`.

The preconditions are satisfiable. The reviewer witnesses are respectively
`N=8`, `N=8`, `N=7`, and `N=9`. For each, the trusted canonical, submitted
Python function, main K formula, and claimed result agree. Exact output is in
[`evidence/concrete-witnesses-summary.log`](evidence/concrete-witnesses-summary.log),
and the independent witness checker is
[`evidence/claim_witnesses.py`](evidence/claim_witnesses.py).

### Pinning and control flow

`verification.k` adds one fresh entry syntax item and one rule. The rule does
not replace the function result with a summary or oracle. It rewrites the fresh
entry item to a normal supplied-semantics `Call` of a closure whose parameter,
body, return, Boolean operation, comparisons, modulo expression, constants, and
definition environment are exactly the normalized submitted `solution.mpy`
AST. Its `...` preserves any trailing continuation and every configuration cell
is framed unchanged.

The direct closure harness deliberately omits the module-level function-name
binding. That omission cannot influence this body: its only lookup is local
parameter `n`. The bridge-free real-module proof in Stage 3 independently
executes `#loadAll`, the actual `FuncDef` binding, name lookup, and the same call
for arbitrary `N`, obtaining the same formula using only supplied semantics.
Thus the harness is pinned to the real submitted function rather than a
substituted algorithm.

There are no loop or helper claims. The function body itself executes:
callee and argument evaluation, frame allocation, parameter binding, local name
lookup, short-circuit `and`, integer comparison, modulo, equality, `Return`,
frame pop, and state restoration all use supplied semantic rules.

The target is result-constraining: the universal target is a specific Boolean
formula in `N`, and each corollary targets a concrete Boolean. It is neither a
free variable, tautology, nor one-way implication.

Stage result: pass.
