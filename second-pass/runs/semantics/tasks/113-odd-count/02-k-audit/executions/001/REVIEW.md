## 2. Program fidelity and candidate-versus-canonical checks

### Natural-language contract

For an input list of digit-only strings, return a list of equal length. For each input string, count its odd decimal digits, call the count `n`, and return:

```text
the number of odd elements {n}n the str{n}ng {n} of the {n}nput.
```

The documented domain is Python `list[str]`, with every character in every string an ASCII decimal digit. The canonical implementation at `/reference/canonical.py:18-21` computes the same count with `sum(int(d) % 2 == 1 for d in arr)`.

### Source inspection

`/candidate/solution.py:1-20` iterates over every input string, resets `count`, adds `int(digit) % 2` for every character, constructs the sentence with four decimal renderings of the count, appends it, and returns the accumulated list. For the allowed characters `0` through `9`, `int(digit) % 2` is exactly 0 for an even digit and 1 for an odd digit. Empty strings yield count 0, and an empty input yields an empty output.

The candidate uses a loop-based rewrite rather than the canonical generator expression. That difference is immaterial on the stated domain.

## 4. Adequacy and real-program pinning

### Claims in plain language

`digit-loop` at `spec.k:6-41`:

- Precondition: `CS` is an ASCII digit code sequence (`allDigit(CS)`).
- Start: the actual inner-loop body iterates over `str(CS)` with current `count = N` and prior `digit = D`.
- Postcondition: the continuation is resumed, `count` becomes `oddDigitsFrom(N, CS)`, `digit` becomes the last character (or remains `D` for an empty sequence), and the other listed locals are unchanged.

`outer-empty` at `spec.k:43-82`:

- Precondition: none.
- Start: the remaining outer iterable is empty and all post-iteration locals are reset.
- Postcondition: the continuation resumes with the accumulator heap list and locals unchanged.

`outer-loop` at `spec.k:84-131`:

- Precondition: the head code sequence and all remaining values are valid digit strings.
- Start: the outer loop has one or more remaining strings, an accumulator list `ACC`, and reset locals.
- Postcondition: the entire remaining loop is consumed, locals are reset, and the heap list is `oddCountFrom(ACC, remaining-input)`.

`target` at `spec.k:133-162`:

- Precondition: every value in `INPUT` is a string and every character code is 48 through 57.
- Start: load `ODD-COUNT-PROGRAM` and call `odd_count(list(INPUT))` from the initial configuration.
- Postcondition: return `ref(0)`; install the expected function closure in module scope; allocate exactly heap location 0 containing `list(oddCountSpec(INPUT))`; restore the empty stack and `noRet`; leave no exception and exit code 0.

The entry postcondition is not a free variable or tautology. It fixes the return reference, heap address, list content, allocation counters, scopes, stack, return state, exception, and exit code. The false mutation in Stage 6 confirms that the result constraint is discriminating.

### Program identity

### Reachable opaque result

orients fixed integer rendering into that opaque symbol, while the postcondition independently uses the same symbol through `oddText`. ### Inner operational bridge: concrete false conclusion

The rule at `verification.k:132-167` consumes the whole inner `For` and writes the mathematical summary. The standalone `digit-loop` claim does start at `#loop`, so it cannot use this `For` rule. However, that theorem pins both module and builtin scopes. The rule does not: its `...` accepts any scope 0 and any scope -1. It therefore accepts configurations outside the theorem’s justification domain.

[05_inner_shadow_witness.k](evidence/05_inner_shadow_witness.k) uses the intended digit input `"1"` but binds global `int` to a legal one-argument closure that always returns 0:

- With the candidate rule, `kprove ... --depth 1` exits 0 and prints `#Top`, asserting final `count = 1`; see [05_inner_shadow_candidate.log](evidence/05_inner_shadow_candidate.log).
- A separately rebuilt definition with only this bridge removed executes the same ground body and ends with `count = 0`; the candidate conclusion is rejected with a final stuck configuration, exit 1. This is a concrete false conclusion enabled by the rule over its stated domain. The real entry does not shadow `int`, but a globally false proof rule cannot be justified by calling its bad states unreachable; it must pin the binding established by its connection theorem.

### Outer operational bridge: assumed task result and concrete false conclusion

The rule at `verification.k:210-243` matches:

```text
#loop(list(INPUT), Name("digits"), ODD-OUTER-BODY)
```

and replaces the entire loop with:

```text

```

This is the task’s property-bearing computation, not a low-level primitive. It reads the mathematical precondition and writes exactly the summary used in the entry postcondition.

There is no independent connection theorem:

- the `outer-loop` claim starts at the same `#loop` redex;
- with the candidate definition it closes with `#Top` at `--depth 1`, proving that no body execution is needed ([05_candidate_outer_depth1.log](evidence/05_candidate_outer_depth1.log));
- removing only the rule still builds successfully ([05_no_outer_build.log](evidence/05_no_outer_build.log));

An unbounded bridge-free diagnostic was manually stopped with SIGINT after about 60 seconds and is not used as a candidate verdict; it is recorded only in [05_no_outer_kprove_outer.log](evidence/05_no_outer_kprove_outer.log).

The rule is also false over its own match domain. [05_outer_shadow_witness.k](evidence/05_outer_shadow_witness.k) uses intended input `["1"]` but globally shadows `str` with a legal closure returning `""`:

- the candidate rule proves the ordinary odd-count summary at depth 1, exit 0 and `#Top` ([05_outer_shadow_candidate.log](evidence/05_outer_shadow_candidate.log));

More fundamentally, on the actual entry path the same rule simply assumes the result it is supposed to establish.

Stage result: the fixed semantics soundly covers the submitted constructs on the intended path, but both candidate priority operational bridges violate binding/context containment. ## 7. Proven versus assumed accounting

### What the successful reachability run actually establishes

Under the supplied semantics **plus every rule in candidate `verification.k`**, and for an algebraic list satisfying `validDigitStrings`, the candidate theory can reach a final configuration returning `ref(0)` whose heap contains `list(oddCountSpec(INPUT))`, with the stated scopes, counters, stack, return state, exception state, and exit code.

That statement is conditional on the following two property-bearing axioms:

1. the inner `For` can be replaced by `oddDigitsFrom`/`lastDigit`; and
2. the entire outer `#loop` can be replaced by `oddCountFrom`.

The second axiom is effectively the theorem. Consequently, the successful reachability run does not establish the same result by executing the real outer loop under the fixed semantics.
