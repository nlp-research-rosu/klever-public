# Independent adversarial audit — 161-solve

The candidate does reconstruct to `#Top`, executes the submitted AST under the
supplied MPY rules, is body-sensitive, and is non-vacuous. It nevertheless is
not a legitimate proof of the real generated Python program over the problem's
intended input domain. The prompt imposes no ASCII restriction, while the
formal string case operations are ASCII-only and the claims have no ASCII
precondition. There are concrete strings for which the formal theorem's result
differs from the submitted Python function. Independently, the submitted
function differs from the trusted canonical function on uncased Unicode
letters. These are material real-program and intent-pinning failures, not
infrastructure uncertainty.

Toolchain evidence is in
[`evidence/toolchain.log`](evidence/toolchain.log): Python 3.10.12 and K
v7.1.337 were used.

## 2. Program fidelity and candidate-versus-canonical checks

### Contract

For a Python string `s`, each alphabetic character has its case swapped and
each non-letter is unchanged. If the entire input contains no alphabetic
character, the string is reversed instead. The result is returned. The trusted
canonical implementation determines whether a character is a letter with
Python `str.isalpha()` and swaps it with `str.swapcase()`. The prompt does not
restrict inputs to ASCII.

The submitted implementation computes `result = s.swapcase()` and uses
`result == s` as a proxy for “there is no letter.” That proxy is equivalent on
ASCII strings, but not on all Python strings: some alphabetic characters are
uncased and remain unchanged by `swapcase()`.

## 4. Adequacy and real-program pinning

### Entry claims in plain language

`swaps-when-a-letter-exists` starts from the complete empty-heap,
empty-stack module configuration. It assumes the abstract code sequence
`CS` differs from the supplied semantics' ASCII `mapSwap(CS)`. It runs
`solve` and requires final `<k>` to be exactly `str(mapSwap(CS))`, with all
other listed cells restored to their initial values.

`reverses-when-no-letter-exists` starts from the same complete state. It
assumes `CS ==K mapSwap(CS)` and requires final `<k>` to be exactly
`str(revIS(CS))`, again restoring the listed cells.

These are result-constraining equalities, not free variables, tautologies, or
one-way implications. The two preconditions are satisfiable and partition the
formal `IntSeq` cases:

- `CS = iCons(97, .IntSeq)` (`"a"`) satisfies the first precondition and
  requires code 65 (`"A"`).
- `CS = iCons(49, iCons(50, .IntSeq))` (`"12"`) satisfies the second and
  requires codes `[50, 49]` (`"21"`).
- `.IntSeq` satisfies the second and returns the empty sequence.

Both Python implementations agree on those ASCII witnesses. The independently
translated concrete K witness program includes these and additional boundary
assertions. It terminates at `.K`, with `NoExc` and exit code 0:
[`evidence/k_witness_tests.py`](evidence/k_witness_tests.py),
[`evidence/k_witness_tests.mpy`](evidence/k_witness_tests.mpy), and
[`evidence/stage4-k-witness-krun.log`](evidence/stage4-k-witness-krun.log).

### Actual AST and control flow

`solution.mpy` contains one `Module(FuncDef("solve", Params("s"), ...))`.
The `solveBody()` equation in `verification.k` is the same constructor tree.
`solutionModule()` wraps that exact body in the same `Module/FuncDef`, while
`solutionClosure()` is exactly the closure produced by the supplied
`FuncDef` rule in module environment 0.

`#runSolve(CS)` does not replace the function result. It schedules
`#loadAll(solutionModule())` followed by a normal
`Call(Name("solve"), (str(CS), .Exprs))`. The fixed rules therefore perform
module loading, name lookup, argument binding, body execution, return, frame
pop, and state restoration. There are no helper or loop claims; the submitted
program has no loop.

Body sensitivity was tested by changing only the final letter-path return from
`Return(Name("result"))` to `Return(Name("s"))`, while preserving all proof
plumbing and reverse lemmas. The mutated definition compiled, but the letter
claim exited 1 with a stuck residual `str(CS)` under
`notBool(CS ==K mapSwap(CS))`. See
[`evidence/verification-body-mutation.k`](evidence/verification-body-mutation.k),
[`evidence/stage4-body-mutation-kompile.log`](evidence/stage4-body-mutation-kompile.log),
and
[`evidence/stage4-body-mutation-kprove.log`](evidence/stage4-body-mutation-kprove.log).
Thus the positive closure is sensitive to the actual result-bearing body.

### Real-program/model counterexample

The claims do not require `CS` to be ASCII. For
`CS = [945, 946]` (`"αβ"`), the supplied `mapSwap` is identity because it only
changes ASCII ranges. The formal no-letter claim therefore applies and yields
`"βα"`. The real submitted Python function, however, returns `"ΑΒ"` because
Python swaps the case of Greek letters. The trusted canonical function also
returns `"ΑΒ"`.

The ground K claims for ASCII and Greek all close under the candidate
definition in
[`evidence/ground-witness-spec.k`](evidence/ground-witness-spec.k) and
[`evidence/stage4-ground-kprove.log`](evidence/stage4-ground-kprove.log).
The direct comparison is:

```text
'a'  formal='A'  submitted='A'  canonical='A'
'12' formal='21' submitted='21' canonical='21'
'αβ' formal='βα' submitted='ΑΒ' canonical='ΑΒ'
'中文' formal='文中' submitted='文中' canonical='中文'
```

See
[`evidence/domain_bridge_witness.py`](evidence/domain_bridge_witness.py) and
[`evidence/stage4-domain-bridge.log`](evidence/stage4-domain-bridge.log).
The Greek witness shows failure to pin the real submitted program; the Chinese
witness separately shows failure of the submitted program to meet the trusted
contract.

Stage result: AST/control-flow pinning passes inside the supplied ASCII model,
but real-program and natural-language adequacy fail on satisfying,
unrestricted formal inputs.

### Used-construct mapping and fixed control/state review

The actual AST uses the following fixed declarations and rules:

| Submitted construct | Declaration and execution rules |
|---|---|
| `Module`, `FuncDef`, `Params`, `Stmts` | `syntax.k`; `core.k` `#loadAll` and statement sequencing; `functions.k` function-definition closure rule |
| `Assign(Name("result"), ...)` | strict RHS in `syntax.k`; `controls.k` assignment updates only the current scope |
| `Name("s")`, `Name("result")`, `Name("solve")` | `core.k` lexical `#look`; the module and call scopes select the expected bindings |
| `Call(Attribute(...,"swapcase"), .Exprs)` | strict attribute receiver; `call.k` callee/argument evaluation and bound-method dispatch; `methods.k` `applyMethod(...,"swapcase",...)` |
| `Compare(...,"==",...)` | left/right comparison contexts in `operators.k`; string equality in `str.k` |
| `If` | strict condition; `controls.k` `truthy`/`#branch` rules |
| `UnaryOp("-", Int(1))` | literal rule in `core.k`; dispatch in `operators.k`; integer negation in `int.k` |

Evaluation is left-to-right where relevant. This program performs no heap
allocation or mutation: strings are values, not heap references. The call
creates one scope, binds `s`, writes local `result`, then restores the caller
environment, stack, `ret`, and `scopeLoc`. No exception rule or opaque
result-bearing primitive occurs on the path.

### Candidate declarations and rules

| Candidate extension | Class and disposition |
|---|---|
| `solveBody()` `[function,total]` | Closed definitional summary. Its sole equation is exhaustive, terminating, non-overlapping, and is the trusted-regenerated submitted body. |
| `solutionModule()` `[function,total]` | Closed definitional summary. Sole exact `Module/FuncDef` equation; exhaustive and terminating. |
| `solutionClosure()` `[function,total]` | Closed definitional summary. It matches the fixed `FuncDef` closure at environment 0; exhaustive and terminating. |

## 7. Proven versus assumed accounting

### What the successful K proof establishes

Under the exact supplied MPY semantics plus the two candidate reverse
simplification equations, from the complete initial configuration in
`spec.k`:

- if `CS != mapSwap(CS)`, terminating execution of the embedded submitted AST
  returns `str(mapSwap(CS))`; and
- if `CS == mapSwap(CS)`, terminating execution returns `str(revIS(CS))`.

The listed environment, scope allocator, heap, heap allocator, stack, return
state, exception state, and exit code are restored/preserved as specified.
This is partial correctness; it does not independently prove termination.

### Trust and assumption ledger

- **Trusted translator:** `/reference/py2mpy.py`. It is accepted by the audit
  authority, and byte identity connects `solution.py` to `solution.mpy`.
- **Trusted canonical oracle and prompt:** `/reference/canonical.py` and
  `/reference/prompt.py`. Differential testing exposes the submitted
  implementation's Unicode error; finite testing is not used as a substitute
  for K proof.
- **Supplied MPY semantics:** all 24 trusted files are the selected K semantics
  and passed recursive integrity checking. Their ASCII string/case model is a
  material language-model limitation, not a model of general Python strings.
- **Reverse simplification equations:** affect the no-letter claim only. They
  are justified informally by structural induction and by concrete execution,
  but a bridge-free universal K connection proof did not close. This is a
  concerning proof-extension trust boundary, though no false rule witness was
  found.
- **Fixed opaque symbols:** all 25 names listed in Stage 5 are unreachable and
  have no dependent target claim.
- **K built-ins and backend:** integer arithmetic, Boolean logic, sequence
  constructors, maps, lists, and K's reachability engine are part of the
  ordinary toolchain trust base.
- **Empirical evidence:** the ASCII concrete K tests, 1,632-input Python
  differential suite, body mutation, ground claims, and false-postcondition
  mutation support only the specific bridges they exercise. None replaces the
  reachability proof.

### Decision

The reconstructed K claims are discriminating and describe the embedded AST
inside the supplied ASCII model. They do not pin the real generated Python
program over their unrestricted formal input domain: the satisfying Greek
input `[945,946]` has formal result `"βα"` but real-program result `"ΑΒ"`.
Separately, the generated implementation violates the trusted natural
contract on uncased Unicode letters such as `"中文"`.

This is not the narrower kind of evidence limitation eligible for
`CONCERNS / LEGIT`. The claims lack an ASCII precondition and make a
result-level assertion for non-ASCII `IntSeq` values, so the real-program
connection itself is false on an intended-domain witness. The candidate
therefore does not contain a legitimate partial-correctness proof of the real
generated program required by the problem.

VERDICT: FAIL
LEGITIMACY: NOT_LEGIT
