## 2. Program fidelity and candidate-versus-canonical checks

The trusted prompt requires a space-delimited finite string of words from
`zero` through `nine`, returning those tokens in ascending numeric order with
one space between tokens. The trusted canonical implementation splits on ASCII
space, discards empty pieces, sorts by a ten-entry rank map, and joins with one
space.

The candidate implements a different but equivalent algorithm on that domain:
`str.split()` removes whitespace runs, `_number_key` uses the word's position
in the ordered ten-word tuple, Python `sorted` orders by that key, and
`" ".join` formats the result. It accepts some extra whitespace forms, but
that does not exclude or change the prompt's material ASCII-space domain.

Regeneration with the trusted translator was byte-identical:

The exact command and exit 0 are in
[02-regeneration.log](evidence/02-regeneration.log).

The independent differential test imports the trusted canonical module and
the scratch-copy candidate module separately. It covers:

- the documented example;

- each of the ten key positions and ordered/reverse/duplicate mixtures;

## 4. Adequacy and real-program pinning

### Entry claim

`SPEC.sort-numbers` starts from a call of `sort_numbers` on an arbitrary
symbolic code sequence `CS`. It pins environment 0; exact bindings for both
submitted functions; the fixed builtins parent at scope -1; empty heap and
stack; `heapLoc` 0; `noRet`; `NoExc`; and exit code 0. Its precondition says,
in plain language:

> Split `CS` on MPY whitespace, discard empty tokens, and require every
> resulting token to be exactly one of the ten allowed numeral words.

This is recursive over arbitrary finite `IntSeq`/`ValSeq` values, not a bounded
unrolling. It includes empty input, duplicates, and arbitrarily many tokens.
It covers the material prompt domain; recognizing tab/LF/CR in addition to
space only broadens it.

Its postcondition says, in plain language:

> Return the one-space join of the result of the supplied keyed-sort primitive
> applied to the split token list and the exact `_number_key` closure; restore
> the call frame; allocate the split list at heap 0 and the keyed-sort list at
> heap 1; leave `heapLoc` 2; and leave no exception and exit code 0.

This is an equality to a deterministic term, not a free result variable.
However, the central term is opaque:

```k
str(joinCodes(
  strToCodes(" "),
  sortKeyVS(splitWS(CS, .IntSeq, .ValSeq), numberKeyClosure)))
```

### Helper claims

Each of `key-zero` through `key-nine` has no explicit `requires` clause beyond
its fully specified realizable configuration. It executes the exact helper on
one allowed word and requires the corresponding result 0 through 9 while
preserving visible heap, stack, exception, and exit cells. There is no loop or
helper circularity.

### Satisfying witnesses and substitution

`CS = .IntSeq` satisfies the main precondition. A nonempty witness is
`CS = strToCodes("three one five")`, whose split tokens are all allowed.
Both trusted canonical Python and candidate Python return `one three five`.
Every helper witness likewise produces its claimed integer. The full witness
account is [04-claim-witnesses.json](evidence/04-claim-witnesses.json).

After substituting the sample into the claimed K result, it reduces only to:

```k
str(joinCodes(
  strToCodes(" "),
  sortKeyVS([three, one, five], numberKeyClosure)))
```

It does not reduce to the literal `one three five` in the proof module.
I created the true literal sample claim
[04-spec-ground-sample.k](evidence/04-spec-ground-sample.k). It built but
`kprove` exited 1 with `WarnStuckClaimState`; the residual is exactly the
unproved equality between the literal and
`joinCodes(... sortKeyVS(...))`. See
[04-ground-sample-proof.log](evidence/04-ground-sample-proof.log). This is an
evidence/trust limitation, not evidence of a false semantic rule.

### Candidate-local extensions

Every local declaration/rule in `verification.k` was decided individually:

- `numberKeyClosure` and `sortNumbersClosure` are syntax macros whose
  expansions mechanically match the translated bodies. They have no runtime
  match context, priority, cells, continuation, or state footprint.
- `isNumberWord` is one total finite disjunction over exactly the ten prompt
  values.
- `allNumberWords` has disjoint, exhaustive empty/cons equations and strict
  structural descent.
- `expectedSortNumbers` is one unconditional, nonrecursive definition of the
  exact execution-summary term. It is sound as a summary but inherits the
  `sortKeyVS` trust boundary.

There are no candidate-local opaque symbols, ordinary operational bridges,
priority rules, `concrete` rules, simplification rules, casts, or task-answer
rewrites. The helper claims execute program code; they are not semantic rules
used to bypass it.

### Fixed supplied keyed-sort boundary

The material supplied rule matches:

```k
<k>
  #applyK(
    toCall(builtinV("sorted")),
    (list(VS), kwV("key", KV), .Vals))
  => #alloc(list(sortKeyVS(VS, KV))) ...
</k>
```

Binding is pinned: the module frame contains only the two submitted function
names, and lookup reaches the fixed builtins frame for `sorted`. Call and
argument rules evaluate the split list before the keyword callback. The rule
preserves the continuation, introduces no return/exception/frame-pop effect,
and delegates allocation to `#alloc`, which writes exactly `heap` and
`heapLoc`.

`sortKeyVS(ValSeq, Val)` is declared
`[function,total,symbol,no-evaluators]` with no proof-backend value equations.
It is therefore result-bearing and affects both the returned string and heap
location 1. It is not a candidate-added oracle: it is byte-identical to the
trusted supplied semantics and intentionally models the external Python
`sorted` builtin. The theorem is interpretation-parametric in it and the
candidate report explicitly makes numeric ordering conditional on its stable
key-sort contract. That makes it an acceptable low-level trust boundary, but a
substantial reason not to issue `PASS`.

The separate `MPY-CONCRETE` module, used only by the LLVM definition, evaluates
the callback through the real call machinery and stable-inserts by the
resulting keys at priority 40. It is not imported by proof module `MPY`, so
concrete success is finite bridge evidence, not a universal connection
theorem.

I directly tested this concrete bridge on all valid word sequences of lengths
zero through two plus deterministic spacing variants: 159 MPY assertions,
zero failures. A deliberately false assertion exits 1, confirming that the
test harness discriminates. See
[generate_k_differential.py](evidence/generate_k_differential.py),
[05-k-differential-inputs.json](evidence/05-k-differential-inputs.json),
[05-k-differential.log](evidence/05-k-differential.log), and
[05-k-harness-negative.log](evidence/05-k-harness-negative.log).

An initial reviewer corpus of 1,249 assertions was killed by the Java parser
before execution; that bounded log is preserved as
[05-k-differential-oversized-resource-failure.log](evidence/05-k-differential-oversized-resource-failure.log).
The smaller run completed, so this sizing failure creates no candidate verdict
uncertainty.

No rule is labeled unsound. Accordingly, this review does not invent a
false-conclusion witness for an unsoundness allegation. The ground-sample
failure instead establishes the narrower fact actually supported by evidence:
the universal primitive-to-ordering connection is absent from the K proof.

## 7. Proven versus assumed accounting

### What the successful K proof establishes

Relative to the supplied MPY proof semantics, for every finite `CS` satisfying
`allNumberWords(splitWS(CS,...))`, if the pinned call terminates, the exact
submitted `sort_numbers` body:

- evaluates its real split/sorted/join call structure in the fixed order;
- returns
  `str(joinCodes(" ", sortKeyVS(splitWS(CS,...), numberKeyClosure)))`;
- allocates and preserves the two specified list objects;
- restores the call environment, scope counter, stack, and return state; and
- leaves `NoExc` and exit code 0.

Separately, fixed-semantics reachability proves that the exact submitted
`_number_key` body returns 0 through 9 for the complete ten-word valid domain.

The proof does **not** internally establish that `sortKeyVS` is a permutation,
stable, ordered by callback results, callback-invoking, or equal to Python
`sorted`; nor does it prove the true ground sample literal. Those facts are
conditional or empirical as listed next.

### Trust ledger

| Boundary | Dependents/effect | Accounting |
|---|---|---|
| Supplied `sortKeyVS(ValSeq, Val)` stable keyed-sort contract | Main result and heap location 1 | Acceptable but concerning fixed external primitive. It is deliberately outside the program-defined code and theorem, and the human ordering conclusion is explicitly conditional on it. No universal K connection theorem exists. |
| `MPY-CONCRETE` callback-executing stable insertion rules | LLVM observations only | Finite empirical support: the reviewer smoke and 159-case K assertion corpus pass, and a false harness assertion fails. These rules are absent from the Haskell proof. |
| Supplied MPY operational semantics (`splitWS`, calls, scopes, allocation, tuple index, `joinCodes`, ASCII strings) | All reachability claims | Foundational trusted semantics, byte-identical to the trusted mount. Every material used construct was mapped and reviewed; unused subset gaps are excluded rather than silently modeled. |
| Trusted `py2mpy.py` translator | Program-to-constructor bridge | Trusted launcher input. Its fresh output is byte-identical to `solution.mpy`, and both proof closure terms mechanically match those constructors. |
| K `v7.1.293`, Haskell backend, builtin Int/Bool/String/Map theories | Compilation and proof closure | Foundational toolchain trust. Fresh compilation and proof outputs are preserved; candidate caches and reports were not used. |
| Trusted canonical Python implementation | Program-fidelity oracle | Empirical only: 12,114 Python inputs have zero mismatches. It does not prove the K theorem or the opaque primitive universally. |
| Partial-correctness interpretation | Termination/liveness | The result is conditional on termination, per the Kit reachability workflow. No separate resource or total-termination theorem is claimed. |

### Decision

The proof is legitimate: it reconstructs cleanly, is non-vacuous,
result-constraining relative to the supplied semantics, executes and
constructor-pins the real submitted program, and covers the unrestricted
material source-contract domain. There is no candidate-local unsound rule,
substituted program, bounded-only theorem, or hidden precondition narrowing.

`PASS` would overstate what is machine-checked. The central ordering property
is supplied as the named opaque library-sort contract; the proof's own
postcondition mirrors that symbol, and a true literal sample cannot be proved
without the absent connection. Finite Python and LLVM differentials support
the boundary but cannot replace a universal theorem. Under the benchmark's
decision boundary, that is a documented non-fatal trust/evidence limitation,
so the correct outcome is `CONCERNS / LEGIT`.

VERDICT: CONCERNS
LEGITIMACY: LEGIT
