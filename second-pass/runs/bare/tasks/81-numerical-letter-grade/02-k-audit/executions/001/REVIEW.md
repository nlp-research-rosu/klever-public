# Independent adversarial audit: 81-numerical-letter-grade

## Executive decision

The candidate contains several genuine, freshly reproducible K reachability
proofs, but it does not contain a proof of the requested function for an
arbitrary input list. Its only top-level symbolic theorems cover the empty list
and a list of length one; the only longer top-level theorem is the single
concrete prompt example. The two loop-step claims establish one iteration at a
time but no claim states or proves the arbitrary-list result. The unused
`expectedGrades` function makes this omission especially visible.

There is also a real generated-semantics mismatch. `semantic.k` assigns exact
decimal rational meanings to Python float literals. When a runtime Python float
is represented by its actual exact binary ratio, the K execution disagrees with
both Python implementations at intended threshold inputs 3.7, 2.7, and 1.3.
Thus the successful claims concern a narrower exact-decimal abstraction, with
no proved connection to the real Python float execution.

These are material adequacy and real-program-model failures. Successful fresh
`#Top` results and a successful non-vacuity probe do not repair them.

## 2. Program fidelity and candidate-versus-canonical checks

### Natural-language contract

For each GPA in the input list, return a letter in the same position using this
strict decision table:

| Condition, in branch order | Grade |
|---|---|
| `gpa == 4.0` | `A+` |
| `gpa > 3.7` | `A` |
| `gpa > 3.3` | `A-` |
| `gpa > 3.0` | `B+` |
| `gpa > 2.7` | `B` |
| `gpa > 2.3` | `B-` |
| `gpa > 2.0` | `C+` |
| `gpa > 1.7` | `C` |
| `gpa > 1.3` | `C-` |
| `gpa > 1.0` | `D+` |
| `gpa > 0.7` | `D` |
| `gpa > 0.0` | `D-` |
| otherwise | `E` |

The strict inequalities mean, for example, that exactly 3.7 is `A-`, exactly
3.0 is `B`, exactly 0.7 is `D-`, and exactly 0.0 is `E`. The prompt does not
state a formal 0-to-4 precondition; the trusted canonical function applies the
same branch chain to any ordered numeric input.

## 4. Adequacy and real-program pinning

### Plain-language claim inventory

1. `empty-input` starts `solutionProgram` with an empty input, empty
   environment, and no result. It requires termination with empty `grades` and
   `result` bindings and an empty returned list.
2. `all-single-grades` starts `solutionProgram` on exactly one `num(P,Q)`,
   requires `Q > 0`, and requires the environment and returned list to contain
   exactly `expectedGrade(P,Q)`.
3. `loop-step-new-variable` starts directly at a loop head whose remaining
   input begins with `num(P,Q)`, with no prior `grade` binding, arbitrary
   original grades and arbitrary accumulated output. For `Q > 0`, it proves
   one body execution appends `expectedGrade(P,Q)`, binds `grade`, and reaches
   the loop on the arbitrary tail.
4. `loop-step-existing-variable` proves the same one-iteration transition when
   an old `grade` binding already exists.
5. `loop-empty` proves that an empty loop term is consumed.
6. `prompt-example` runs `solutionProgram` on the five concrete prompt inputs
   and fixes the complete final environment and return list.

The top-level result is constrained in all three entry claims; it is not a free
variable, tautology, or implication-only postcondition. The loop-step results
are also constrained via the exact update of the `result` binding.

### Satisfiable preconditions and concrete substitutions

All entry preconditions are realizable:

- `empty-input`: input `.Vals`, environment `.Map`, result `noResult`;
- `all-single-grades`: `P = 4`, `Q = 1`, producing `A+`;
- `prompt-example`: the exact five rational inputs printed in the claim.

The loop-step preconditions are realizable with `P = 4`, `Q = 1`,
`REST = .Vals`, `ALL = .Vals`, and `OUT = .Vals`; the existing-variable
variant may take any old grade value. `loop-empty` is ground-realizable
immediately. The corresponding Python and K executions occur in the Stage 3
normal, empty, and boundary logs.

### Program pin

The entry claims start from the proof-local nullary function
`solutionProgram`, not directly from the parsed file. That helper does not
summarize a result or skip execution: its sole equation expands to the module
AST, and `gradingBody` expands to the complete submitted branch tree. An
audit-only equality claim containing the literal submitted constructor tree
closed with `#Top`; see [program-pin.k](evidence/program-pin.k) and
[12c-program-pin.log](evidence/12c-program-pin.log). The earlier
[12-program-pin.log](evidence/12-program-pin.log) and
[12b-program-pin.log](evidence/12b-program-pin.log) preserve two reviewer
drafting diagnostics (empty-list concrete syntax and unsupported bare
functional claims); neither involved a candidate target claim.

Static comparison also confirms that the docstring expression, empty-result
assignment, loop, all 12 tests, 13 appends, and return match
`solution.mpy`. Therefore the claims that do start from `solutionProgram` pin
the submitted AST.

### Material theorem-scope failure

There is no entry claim of the form “for every finite input list, execution
returns the elementwise expected-grade list.” `all-single-grades` is exactly a
length-one theorem. The two loop claims stop after one iteration with a
residual `loop(..., REST)`; they do not state a final result for arbitrary
`REST`. `loop-empty` only handles the base term, and `prompt-example` is one
ground five-element case.

`verification.k` defines `expectedGrades(Vals)`, the natural summary needed by
an arbitrary-list theorem, but `spec.k` never refers to it. This is confirmed
by [21-symbol-usage.log](evidence/21-symbol-usage.log). An informal induction
could be sketched from the step facts, but no K reachability claim states or
machine-checks that induction. Consequently the returned value of the real
function is not proved correct for lists of length 2, 3, 4, or arbitrary
length, except for the one concrete five-element example.

Stage 4 result: FAIL.

### `verification.k`: all 17 rules

`expectedGrade` has 13 guarded equations, in order:

1. `P = 4Q` gives `A+`;
2. `P != 4Q` and `10P > 37Q` gives `A`;
3. `37Q >= 10P > 33Q` gives `A-`;
4. `33Q >= 10P > 30Q` gives `B+`;
5. `30Q >= 10P > 27Q` gives `B`;
6. `27Q >= 10P > 23Q` gives `B-`;
7. `23Q >= 10P > 20Q` gives `C+`;
8. `20Q >= 10P > 17Q` gives `C`;
9. `17Q >= 10P > 13Q` gives `C-`;
10. `13Q >= 10P > 10Q` gives `D+`;
11. `10Q >= 10P > 7Q` gives `D`;
12. `7Q >= 10P` and `P > 0` gives `D-`;
13. `P <= 0` gives `E`.

For `Q > 0` these guards are complete, pairwise disjoint, and exactly state
the mathematical table. `expectedGrade` is a definitional postcondition
summary; it does not replace execution. The body is symbolically executed
before the result is matched to this function, so this is not a smuggled
oracle.

Outside the claimed domain, guards overlap. At `P=0,Q=-1`, both the `A` guard
and the `E` guard are true; backend function ordering selects `A`.
[outside-domain-overlap.k](evidence/outside-domain-overlap.k) and
[16-overlap-to-a.log](evidence/16-overlap-to-a.log) record that reduction;
[17-overlap-to-e.log](evidence/17-overlap-to-e.log) records rejection of the
opposite result. Because every candidate use that affects a claim requires
`Q > 0`, this is a global reuse/definition gap, not an intended-domain
unsoundness witness and not a verdict driver.

`expectedGrades` has two equations: empty maps to empty, and a numeric head
maps through `expectedGrade` recursively. The recursion descends. Its
`[total]` attribute is nevertheless too broad because the declared `Vals`
sort also admits `str`, `bool`, `list`, and `none` heads, for which there is no
equation. The symbol is unused by every claim, as
[21-symbol-usage.log](evidence/21-symbol-usage.log) shows. This is a static
quality defect, not a source of the successful results.

`gradingBody` has one unguarded nullary equation to the complete actual branch
tree. `solutionProgram` has one unguarded nullary equation to the complete
actual module AST. Both are complete, nonrecursive definitional macros. They
name code and then let the ordinary semantics execute it; neither summarizes
or fabricates the result.

### Concrete intended-domain false-behavior witnesses for float rules

The abstract `num(P,Q)` datatype is documented as the exact rational `P/Q`.
A faithful exact-rational representation of Python's runtime float `3.7` is:

```text
P = 4165829655317709
Q = 1125899906842624
```

This satisfies the entry precondition `Q > 0`. Python compares that value to
the identical binary float literal `3.7`, so equality holds and `>` is false;
both trusted canonical and candidate Python return `A-`. In K, the literal
rule makes the threshold exactly `37/10`, and
`10P = 37Q + 2`, so the same exact runtime value is considered greater and K
returns `A`.

The same witness pattern occurs at:

- Python `2.7` =
  `3039929748475085/1125899906842624`: K returns `B`, Python returns `B-`;
- Python `1.3` =
  `5854679515581645/4503599627370496`: K returns `C-`, Python returns `D+`.

The Python inputs, ratios, and results are preserved in
[13-python-float-boundaries.log](evidence/13-python-float-boundaries.log).
The K run on those exact positive-denominator ratios is in
[14-krun-faithful-binary-float-ratios.log](evidence/14-krun-faithful-binary-float-ratios.log).
The mismatch is enabled specifically by the float-literal rules at
`semantic.k:121`, `semantic.k:124`, and `semantic.k:128`, together with the
rational greater-than rule. These are intended table boundaries and satisfy
the symbolic entry domain, so this is a concrete real-program false-conclusion
witness, not merely an untested edge outside the theorem.

One may instead choose an abstraction that maps the human decimal token 3.7
to `37/10`; the ordinary concrete logs show that this mapping matches the
table. But the candidate provides no abstraction relation or connection
theorem from arbitrary runtime Python numeric values to that representation.
Finite Python-versus-Python differential tests cannot supply that theorem.

Stage 5 result: FAIL for real-Python semantic fidelity. The operational model
is otherwise coherent on its declared exact-decimal, positive-denominator
subset.

## 7. Proven versus assumed accounting

### What the successful K proofs establish

Conditional on the candidate's exact-decimal rational semantics and the K
builtins:

- the submitted program returns an empty list on empty input;
- for every `P,Q` with `Q > 0`, it returns the candidate table value on a
  one-element `num(P,Q)` input;
- one loop iteration appends that table value and reaches the next loop head,
  both before and after the loop variable exists;
- the empty loop consumes no computation;
- the concrete prompt example returns the five stated grades in order.

The positive claims are result-constraining, non-vacuous, and execute the
actual pinned AST. There is no operational bridge that replaces the grading
body with `expectedGrade`.

They do **not** establish:

- elementwise correctness for an arbitrary finite input list;
- a top-level result of `expectedGrades(INPUT)` for arbitrary `INPUT`;
- equivalence between exact-decimal `num` execution and real Python binary
  float execution;
- behavior for nonnumeric list elements, nonpositive rational denominators,
  nonempty list literals, aliases, exceptions, or early returns with trailing
  continuation;
- termination as a separate total-correctness theorem.

### Trust ledger

| Boundary | Dependents | Assessment |
|---|---|---|
| K v7.1.293 compiler, Haskell backend, and builtin Bool/Int/Map operations | All builds and proofs | Ordinary low-level trusted proof infrastructure; freshly invoked and reproducibly logged. |
| Trusted `/reference/py2mpy.py` | Program AST identity | Acceptable trusted input. Byte regeneration pins `solution.py` to `solution.mpy`. |

### Validation gates

- Gate A, real-program soundness: FAIL. Program identity and non-vacuity pass,
  but the numeric semantic bridge has concrete satisfying-input
  counterexamples.
- Gate B, intent adequacy: FAIL. No arbitrary-list entry theorem proves the
  function contract.
- Gate C, auditability: the reconstructed commands and finite tests are
  reproducible, but the crucial Python-number abstraction has neither a
  universal connection theorem nor correct boundary evidence.

The candidate therefore proves honest but materially narrower facts. It is not
a legitimate partial-correctness proof of the real generated function over its
intended list input domain.

VERDICT: FAIL
LEGITIMACY: NOT_LEGIT
