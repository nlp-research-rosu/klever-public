# Independent adversarial review: 139-special-factorial

## Executive finding

The candidate contains a fresh-reconstructible, result-constraining K proof of
the submitted constructor term under its own abstract semantics. The proof is
not vacuous, the helper claims are independently proved before being reused,
and the claim term is mechanically identical to the trusted regeneration of
`solution.mpy`.

It is nevertheless not a legitimate proof of the complete HumanEval contract
for the real generated Python program. The contract admits every positive
integer. The submitted implementation is recursively defined and, under the
actual CPython execution model used to run `solution.py`, raises
`RecursionError` on allowed inputs. The generated K semantics has an unbounded
algebraic call stack and no recursion-limit/exception state, so it returns the
mathematical value for the same inputs. The concrete witness `n = 1001` is
decisive:

- K exits 0 and returns a 1,179,817-decimal-digit integer (3,919,265 bits,
  residue 661457452 modulo 1000000007).
- The trusted canonical returns the same integer.
- The submitted `solution.py` raises `RecursionError`.

This is a material loss of the unrestricted positive-integer source-contract
domain, not a finite-testing caveat. Under the benchmark's explicit mapping,
that makes the candidate `FAIL / NOT_LEGIT`, even though the abstract K theorem
is internally sound and non-vacuous.

## 2. Program fidelity and candidate-versus-canonical checks

### Contract and implementations

The trusted prompt states that, for an integer `n > 0`, the function must
return

`n! * (n-1)! * ... * 1!`.

The documented example is `special_factorial(4) == 288`.

The trusted canonical (`/reference/canonical.py:18`) iteratively maintains
`fact_i = i!` and multiplies each cumulative factorial into the result. The
candidate (`/candidate/solution.py`) instead defines:

- `factorial(n) = 1` at `n <= 1`, otherwise
  `n * factorial(n - 1)`;
- `special_factorial(n) = 1` at `n <= 1`, otherwise
  `factorial(n) * special_factorial(n - 1)`.

Those equations are mathematically equivalent to the requested product for
positive integers. The algorithmic difference becomes material at CPython's
recursion boundary.

### Trusted regeneration

From the scratch copy, the exact command

```text
python3 /tmp/audit-work/trusted/py2mpy.py /tmp/audit-work/candidate-src/solution.py
```

produced SHA-256
`1d37d11e67fc48c6f8572fec6701a168293fee886e4499acc9ca78a6f0fa1cc0`,
byte-identical to the submitted `solution.mpy`. The command, `cmp`, hashes, and
exit 0 are in `evidence/stage2-translation.log`.

### Independent differential

`evidence/differential_test.py` independently imports the trusted canonical and
the candidate from explicit scratch paths. It covers the example, base and
recursive branch boundary (`1`, `2`), every input `1..80`, deterministic random
positive inputs, larger representatives, and the recursion boundary. An
"empty" value is inapplicable because this entry point takes one scalar
integer; no-argument behavior is outside the signature. Inputs `-2`, `-1`, and
`0` were observed separately and not counted as contract cases.

The command exited 1 because it found six intended-domain mismatches in that
call context, `n = 996..1001`: canonical returned an integer and candidate
raised `RecursionError`. The precise frame at which CPython rejects recursion
can shift by a few calls with the caller context; `n = 1001` is also confirmed
by a separate direct-call witness. The example and all sampled lower values
agree. See `evidence/stage2-differential.log`.

**Stage 2 result: FAIL for full contract fidelity.** The mathematical rewrite
is correct where it returns, but the actual generated implementation does not
return on all allowed positive integers.

## 4. Adequacy and real-program pinning

### Plain-language claims

`factorial-call` (`/candidate/spec.k:6`) says: for any positive `N`, with the
exact two submitted functions installed and caller variable `n = N`,
evaluating the real call `factorial(n)` reaches the administrative
`returned("factorial", factorialSpec(N), KONT)` state. Its continuation,
caller environment (including arbitrary additional bindings), stack,
function map, and result cell are preserved as specified.

`special-factorial-call` (`/candidate/spec.k:15`) says the analogous statement
for `special_factorial(n)` and `specialFactorialSpec(N)`.

`program-correct` (`/candidate/spec.k:24`) says: for every positive `N`, start
from the exact submitted module, empty functions/environment/stack, and no
result; after the abstract machine finishes, `<k>` is empty, both submitted
functions have been loaded, the environment and stack are empty, and the
result is exactly `specialFactorialSpec(N)`.

All three preconditions are satisfiable. For example, `N = 1`, an empty
continuation and stack, `noResult`, the exact `solutionFunctions` map, and an
environment containing `n |-> 1` satisfy either helper entry. `N = 1` with the
default initial configuration satisfies the whole-program entry. The mutation
residual in Stage 6 independently exposes this concrete base branch.

### Mechanical program identity

The submitted term was regenerated with the trusted translator, parsed using
the fresh proof definition, macro-expanded, and rendered to KORE. Separately,
`solutionProgram` was parsed and macro-expanded to KORE. `cmp` exited 0, and
both files have SHA-256
`4bcf273c99d4c84b19f621c546d509be683c5e422eb5c6df6f525a025dd7513a`.
See `evidence/stage4-program-pinning.log`.

`program-correct` also constrains the final function map to
`solutionFunctions`; successful closure therefore checks that the loader
constructs the same two bodies. There is no external source filename used as a
proxy for the theorem.

### Ground substitution and result constraint

For `N = 4`, the defining equations reduce
`factorialSpec(4)` to `24` and
`specialFactorialSpec(4)` to `24 * 6 * 2 * 1 = 288`. Fresh K, trusted
canonical, and candidate CPython all return 288. Boundary substitutions
`N = 1` and `N = 2` similarly give 1 and 2, confirmed by the concrete log.
The result is not a free existential, tautology, or implication: the
`<result>` cell is rewritten to the exact recurrence value.

### Body sensitivity

I changed the actual executable factorial body from multiplication to
subtraction in all three places that must agree:

- reviewer-mutated `solution.py`;
- trusted regeneration of its `solution.mpy`;
- both `solutionFunctions` and `solutionProgram`.

The mutated translated term and mutated claim term were mechanically identical
(SHA-256
`8dbad5c1075c671e9a9b867f54afa464bb3d6863e3b6f11aea4bbbd12a778318`).
The fresh mutated definition built successfully. The factorial proof then
exited 1 with the exact unmet equality:

```text
N -Int factorialSpec(N -Int 1)
  =/= N *Int factorialSpec(N -Int 1)
```

This changes the term actually executed by the claim, not merely an ignored
source file. See `evidence/body-sensitivity.patch`,
`evidence/stage4-body-mutation-build.log`, and
`evidence/stage4-body-mutation-kprove.log`.

**Stage 4 result: PASS for constructor-level identity, result constraint, and
body sensitivity. Adequacy still fails at allowed real-CPython inputs because
the language model omits the recursive exception.**

### Reachability claims

The two helper claims are derived execution lemmas. Their match domain includes
arbitrary `KONT`, caller stack, caller result, and extra caller bindings; their
proofs establish exactly that broad context, so there is no continuation-frame
containment gap. Both program-defined bodies execute under fixed rules before
the tagged return is observed. `program-correct` then uses these independently
proved lemmas. No claim is an opaque trusted primitive.

Rule heads and guards are disjoint where they share administrative symbols:
true/false branches, `"*"`/`"-"` arithmetic, and the two total-function cases.
No priority can hide an overlap because no local priorities exist.

This is a false control/result conclusion about the real generated program on
the intended domain, not an off-path hypothetical. The exact bounded command

inadequate for the real submitted CPython program over the stated domain.**

## 6. Fresh non-vacuity test

The candidate supplied no mutation artifact, so I created an independent

two freshly proved helper claims and changes only the final result obligation

```text
result(specialFactorialSpec(N) +Int 1)
```

establishes both postcondition discrimination and body sensitivity.

**Stage 6 result: PASS.**

## 7. Proven versus assumed accounting

### What the successful K proof establishes

Conditional on the submitted abstract semantics and K's built-ins, the proof
establishes partial correctness:

> For every mathematical K integer `N > 0`, if the abstract machine executing
> the exact translated module reaches the claimed final configuration, its
> result is `specialFactorialSpec(N)`, where the defining recurrences are the
> ordinary positive factorial and the product of factorials.

The proof does not establish termination; the successful recursive
reachability claims are used coinductively. It also does not, by itself,
establish that the abstract machine covers CPython's exceptional/resource
behavior.

### Trust ledger

| Boundary | Role and dependents | Assessment |
|---|---|---|
| K parser/compiler, LLVM/Haskell backends, `kprove` | Executes and proves every claim | Ordinary toolchain trust; version and fresh commands recorded. |
| K `INT`, `BOOL`, `MAP`, `STRING`, and K-sequence primitives | Integer arithmetic/comparison, guards, environments, function map, continuations | Acceptable low-level primitive boundary for the modeled language. |
| Trusted `/reference/py2mpy.py` | Connects candidate Python AST to `solution.mpy` | Acceptable and strong: candidate translator is byte-identical, regeneration is byte-identical, and expanded KORE equals the claim term. |
| `factorialSpec`, `specialFactorialSpec` | Exact postcondition values used by all claims | Truthfully and totally defined, not opaque, and do not replace execution. |
| Product-of-factorials interpretation | Connects the recurrence to the English phrase | Straightforward informal mathematical induction; not separately machine-checked in K. |
| Helper reachability claims | Summarize recursive program execution for the whole-program claim | Not unproved assumptions: independently close with `#Top` before modular reuse. |

There are no opaque result-bearing symbols, unconstrained oracles,
simplification axioms, operational bridge rules, or hidden trusted candidate
claims. The decisive defect is instead the mismatch between the abstract
runtime proved and the actual generated program required by the unrestricted
contract.
