# Adversarial audit: HumanEval 42 `incr_list`

The candidate's Python implementation is correct on the intended integer-list
domain, its translated constructor program is authentic, and its submitted K
claims freshly print `#Top`. The K result is nevertheless not a legitimate
partial-correctness proof of that program's intended result. Its postcondition
is a proof-local `#incPrefix` value, and the only step connecting successive
prefixes is an unguarded, task-specific operational simplification. That
simplification has no bridge-free connection theorem, bypasses evaluation of a
nested list access, admits a false out-of-bounds conclusion, and is essential
to proof closure.

## 2. Program fidelity and candidate-versus-canonical checks

The trusted contract in `/reference/prompt.py` is: for an input list of
integers, return a list in the same order with one added to every element. The
two documented examples are `[1,2,3] -> [2,3,4]` and the nine-element example
ending in `123 -> 124`. `/reference/canonical.py` implements exactly the list
comprehension `[(e + 1) for e in l]`.

`/candidate/solution.py` uses a different but equivalent loop:

1. initialize a fresh empty `result`;
2. for each `value`, replace `result` by `result + [value + 1]`;
3. return `result`.

It preserves the input and returns a fresh list. Running the trusted translator
on this source regenerated the submitted `/candidate/solution.mpy` byte for
byte; both hashes are
`973649ca065888e3e0d4180da89fc16cdb901ca5dee021a543b095f105ed2c50`
(`evidence/stage2-translate.log`, exit 0).

The independent `evidence/differential.py` imports the trusted and generated
entry points separately. It checks both examples, zero and one loop iteration,
negative/zero/positive values, duplicates, ordered and alternating lists,
100-digit integers, and three seeded samples at every selected length from 0
through 127. It also checks input preservation and result freshness. The exact
50 inputs and both outputs are in `evidence/stage2-differential.log`:

```text

```

This establishes strong finite implementation evidence, not a universal K
proof.

## 4. Adequacy and real-program pinning

### Claims in plain language

`for-invariant` (`/candidate/spec.k:8`) assumes:

- `<k>` contains the exact submitted loop at index `I`, followed by the
  submitted return;
- `<env>` contains `l -> pyList(L)` and
  `result -> #incPrefix(L,I)`;
- `<iter>` may contain anything and `<result>` is `noResult`;
- `0 <= I <= size(L)`.

It concludes that execution terminates with empty `<k>`, changes the
accumulator and result to `#incPrefix(L,size(L))`, and leaves the iterator
unconstrained.

`incr-list-correct` (`/candidate/spec.k:36`) assumes the exact initial cells:
the constructor program applied to `pyList(L)`, empty environment, `noIter`,
and `noResult`. It has no `requires` condition, so every K `List` satisfies its
formal precondition. It concludes that the result is
`#incPrefix(L,size(L))` while leaving final environment and iterator
unconstrained.

Both preconditions are satisfiable. For example, for
`L = ListItem(pyInt(1)) ListItem(pyInt(2))`, the entry state is immediate, and
the loop precondition holds at `I=0` because
`#incPrefix(L,0)` reduces to `pyList(.List)`.

### Program pinning

The entry term really is the submitted program. `kast` parsed both the trusted
regenerated `solution.mpy` and a direct extraction of the claim's `Program`
term. After the demonstrated empty-list surface normalization
`ListExpr(.Exps) -> ListExpr()`, the JSON AST files are byte-identical with
SHA-256
`9a6733ec233af548adde66f0a7d36e4f08e250888830398e7d05178c867803b5`
(`evidence/stage4-program-pinning.log`).

A body-sensitivity mutation changed the `Int(1)` in the actual entry program
term to `Int(2)` while leaving the invariant and result summary unchanged.
The mutation builds but fails with `WarnStuckClaimState`
(`evidence/spec-body-mutation.k`,
`evidence/stage4-body-sensitivity.log`, exit 1). The theorem therefore depends
on the pinned body, not merely an external source filename.

### Result adequacy

The returned value is not a free variable or tautology, but it is not
mechanically constrained to the intended concrete list either.
`#incPrefix(List,Int)` is declared `[function,total]` at
`/candidate/semantic.k:34`, yet its only own reduction is the zero case at
line 121. Positive prefixes remain opaque.

For the satisfying ground input `[1,2]`:

- trusted canonical Python returns `[2,3]`;
- generated Python returns `[2,3]`;
- concrete K matches
  `result(pyList(ListItem(pyInt(2)) ListItem(pyInt(3))))` with `#Top`;
- the literal claimed post-state
  `result(#incPrefix(ListItem(pyInt(1)) ListItem(pyInt(2)),2))`
  matches the same concrete execution with `#Bottom`.

See `evidence/ground_witness.py`,
`evidence/stage4-ground-expected.log`, and
`evidence/stage4-ground-postcondition.log`. No submitted theorem states that
the opaque value equals the concrete element-wise-incremented `pyList`.

Gate B therefore fails even before considering the proof extension's
soundness.

## 5. Rule-by-rule static soundness review

`evidence/rule-inventory.md` exhaustively enumerates:

- all 13 constructor-syntax declarations;
- all 15 runtime/control/function declarations;
- the four-cell configuration;
- all 23 rules in `semantic.k`;
- both simplification rules in `verification.k`;
- both reachability claims;
- every `[function]`, `[total]`, `[simplification]`, opaque symbol, import, and
  used-construct mapping.

There are no local priority or `functional` declarations.

The ordinary concrete path is small and mostly faithful. Initialization,
statement sequencing, assignment, the two loop guards, top-level return,
integer addition, list concatenation, and in-bounds lookup correctly cover the
submitted program. The separate `<iter>` binding is not a general Python scope
model, but it is adequate here because the target only reads `"value"` inside
the loop. The two name-lookup rules overlap if a name is simultaneously in
`<iter>` and `<env>`; that state is not reachable for this target, so it is
recorded as a reuse limitation rather than the verdict basis.

Several `[total]` declarations are not backed by exhaustive equations:
`#eval`, `#add`, and `#at` are partial outside the exact target path, and
`#incPrefix` has no positive-index defining equation. In particular, the
formal entry precondition accepts lists containing non-`pyInt` values even
though concrete addition then sticks.

### Material result-bearing bridge

The decisive rule is `/candidate/semantic.k:110-114`:

```k
rule #add(
       #incPrefix(L, I),
       pyList(ListItem(#add(#at(L, I), pyInt(1)))))
  => #incPrefix(L, I +Int 1)
  [simplification]
```

Classification: result-bearing operational bridge, not merely a name for a
mathematical value. It rewrites the very accumulator-plus-singleton expression
executed by the loop invariant before fixed evaluation of the nested `#at` and
integer `#add`. The proof postcondition depends directly on the same opaque
symbol. There is no bridge-free universal connection theorem; the only
candidate connection is `for-invariant`, which imports this rule and is
therefore circular as a justification for it.

The rule is also globally false as an execution rule. Choose any nonempty
intended integer list and `I=size(L)`. Python/K list indexing at that index is
out of bounds. The direct K term remains stuck, yet the outer bridge fabricates
`#incPrefix(L,size(L)+1)`.

Machine witness:

```text
kprove spec-rule-witness-positive.k ... --spec-module \
  SPEC-RULE-WITNESS-POSITIVE
#Top
EXIT_STATUS: 0

kprove spec-rule-witness-control.k ... --spec-module \
  SPEC-RULE-WITNESS-CONTROL
WarnStuckClaimState
result(#at(L,size(L)))
EXIT_STATUS: 1
```

The witness assumes `size(L)>0`, which has the satisfying intended input
`L=ListItem(pyInt(1))`. Files and full residuals are
`evidence/spec-rule-witness-positive.k`,
`stage5-rule-witness-positive.log`,
`spec-rule-witness-control.k`, and
`stage5-rule-witness-control.log`. The ground substitution additionally
exposes competing normalization through the concrete lookup
(`spec-rule-witness-ground.k`,
`stage5-rule-witness-ground.log`).

At `I=0`, the bridge also overlaps the base equation
`#incPrefix(_L,0) => pyList(.List)`. Reducing the inner prefix first exposes
ordinary list concatenation; applying the outer bridge first produces the
opaque positive prefix. The candidate supplies no confluence lemma equating
those normal forms.

The verification-only rule at `/candidate/verification.k:13-15` assumes
injectivity of this incompletely defined prefix symbol. Prefix injectivity is
ordinary mathematics for genuinely defined prefixes, but here it compounds
the missing value connection. The second verification rule,
`0 <=Int size(L) => true`, is sound.

Finally, removing only the special bridge, rebuilding successfully, and
rerunning the unchanged claims exposes exactly the missing step:

```text
#add(#incPrefix(L,I),
     pyList(ListItem(#add(#at(L,I),pyInt(1)))))
#Equals #incPrefix(L,I+1)
```

The proof then exits 1 with `WarnStuckClaimState`
(`evidence/semantic-no-bridge.k`,
`evidence/stage5-no-bridge-build.log`,
`evidence/stage5-no-bridge-proof.log`). This establishes that closure relies
on the rejected shortcut.

Gate A fails: the task's correctness conclusion has been placed in a
proof-purpose operational equation without the required independent
connection, and that equation admits a concrete/symbolic false-behavior
witness.

## 7. Proven versus assumed accounting

What `#Top` precisely establishes is conditional on the submitted extended
theory:

> For arbitrary K `List L`, the exact constructor program can be symbolically
> summarized from the specified initial cells to a state whose result is the
> proof-local term `#incPrefix(L,size(L))`; the exact remaining loop similarly
> maps `#incPrefix(L,I)` to that final opaque term.

It does not machine-check that this term is
`pyList([pyInt(e+1) for e in L])`.

Accepted low-level trust:

- K v7.1.293 parser, compiler, Haskell backend, and reachability/circularity
  implementation;
- built-in unbounded integers, comparisons, Booleans, K equality, finite maps,
  K lists, list size/concatenation, and K sequencing;
- the mounted trusted translator for the source-to-constructor bridge.

Candidate-local assumptions and dependents:

- `#incPrefix [function,total]`: opaque at positive indices; affects every
  invariant and final result.
- the special `#add` bridge: supplies the task-specific successor equation;
  required by `for-invariant` and therefore by the entry claim.
- prefix injectivity simplification: assists final implication and assumes the
  intended meaning of the opaque symbol.
- name/environment and big-step-expression modeling: affects concrete
  execution; supported only by construct analysis and finite smoke tests.
- generated semantics as a Python model: empirically supported by five exact K
  cases and 50 Python differential cases, not universally proved.
- constructor equality between `solution.mpy` and the claim body:
  mechanically established by the AST comparison.

The differential tests, concrete executions, body mutation, and false-result
mutation are useful evidence for exactly those finite checks. None substitutes
for the missing bridge-free theorem or turns `#incPrefix` into the intended
list.

Gate summary:

- Reconstruction/positive closure: pass.
- Real-program constructor pinning: pass.
- Non-vacuity: pass.
- Gate A real-program soundness: fail.
- Gate B intent/result adequacy: fail.
- Gate C evidence reproducibility: pass for the recorded evidence, but it
  cannot rescue Gates A or B.

Under the benchmark decision boundary, a proof that depends on a materially
unsound, task-answer-bearing semantic shortcut and concludes only an
unconnected opaque result is `FAIL / NOT_LEGIT`.
