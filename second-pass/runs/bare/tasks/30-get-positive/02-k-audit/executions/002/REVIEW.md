# Independent adversarial audit: 30-get-positive

The candidate reconstructs successfully and contains a sound, result-constraining
theorem about the exact submitted constructor term on arbitrary finite lists of
K mathematical integers. It does **not** prove the full source contract. The
trusted prompt asks for the positive “numbers” in a Python `list` and does not
restrict the elements to integers. Both the trusted canonical implementation
and the submitted implementation terminate normally on, for example,
`[-1.5, 0.0, 2.25]` and return `[2.25]`; the K configuration cannot represent
that input because `PyList` is defined only by `cons(Int, PyList)`.

This is a material source-domain restriction. The benchmark instructions
explicitly map that form of otherwise sound-but-limited proof to
`FAIL / NOT_LEGIT`.

## 2. Program fidelity and candidate-versus-canonical checks

order and with duplicates preserved, only the positive numbers in `l`. The two

## 4. Adequacy and real-program pinning

### Formal claims in plain language

The universal entry claim has no additional `requires` clause. Its typed
configuration precondition is: `INPUT` is any finite term of sort `PyList`,
which means a free `nil`/`cons` list whose elements are K mathematical
integers. Its postcondition is that the exact submitted module term reaches
`filterGt(INPUT,0)` while retaining the same `<input>` cell.

The three auxiliary claims say:

1. for a nonempty integer list with positive head `I`, the exact program
   reaches `cons(I, filterGt(REST,0))`;
2. for a nonempty integer list with zero or negative head, it reaches
   `filterGt(REST,0)`;
3. for the empty integer list, it reaches `nil`.

The four remaining target claims are the two documented examples, the empty
case, and an all-nonpositive case, each with a ground expected result.

The RHS of the universal claim is not free: it is a recursive function of the
same `INPUT` variable. Its equations retain a head exactly under `I >Int 0`
and otherwise discard it, so the theorem is result-constraining rather than a
tautology or one-way implication.

### Inventory summary

`semantic.k` contains:

- 12 program/input constructor productions: `Module`, `FuncDef`, `Params`,
  `Return`, `Name`, `Int`, `ListComp`, `Compare`, `CompFor`, `CmpOp`, `nil`,
  and `cons`;
- one `<py>` configuration with `<k>` and immutable `<input>` cells;
- internal syntax `eval(Expr,Map)`;
- partial function `asList(KItem)`;
- recursive function `filterGt(PyList,Int)`;
- six local rules: entry binding, `asList`, exact comprehension evaluation,
  empty filter, retain-positive head, and discard-nonpositive head.

There are no local declarations or rules marked `total`, `functional`,
`simplification`, `concrete`, `owise`, or priority, and no opaque result
symbol. A canonical scan confirms `verification.k` has no simplification
rules. `verification.k` contains only three reachability claims; `spec.k`
contains only the five target claims.

### Construct coverage and rule decisions

Every constructor in trusted-regenerated `solution.mpy` is declared and
matched by the entry or comprehension rule. Omitting unrelated translator
constructs is acceptable in `GENERATED_SEMANTICS`.

- The entry rule selects `"get_positive"`, retains its actual `Return(E)` body,
  binds its actual sole formal name to the external `PyList`, leaves the input
  cell unchanged, and preserves the continuation. It is a harness bridge:
  running a module term means invoke the selected entry point. This is not
  literal Python import behavior, but it is explicit and sound for this task
  harness.
- `asList(L:PyList) => L` is true on its entire match domain. It is deliberately
  partial and is not declared total.
- The comprehension rule matches exactly one generator whose element, target,
  and predicate use the same `X`, looks up the iterable formal `P`, and matches
  the exact `>` integer predicate. On finite integer lists it correctly maps
  this pure comprehension to stable filtering. It preserves the continuation
  and every modeled cell.
- `filterGt(nil,N)` is the correct base value. The positive and nonpositive
  head guards are disjoint and jointly exhaustive over K integers, and both
  recursive equations strictly descend to the tail. There is no overlap or
  nontermination defect.

The comprehension rule is task-shaped and result-bearing:
`filterGt` occurs both in its RHS and the universal postcondition. There is no
bridge-free K theorem against an independently fixed Python semantics. In this
generated-semantics condition, I treat the rule as part of the submitted
language definition and audit it on its merits. Its complete equations,
binding pattern, control preservation, body mutation, and 64 K/Python cases
support the bridge. They do not turn the bridge into a theorem about Python.
This is a named informal/empirical trust boundary, not an unconstrained oracle:
`filterGt` has exhaustive transparent equations, and the opposite results are
rejected by concrete execution and the false-result mutation.

I found no local rule that permits a false conclusion on its declared
integer-list match domain. Accordingly, I make no unsound-rule allegation
requiring a false-conclusion witness. The float witness is instead an adequacy
counterexample: it satisfies the source contract but cannot satisfy the formal
precondition.

The generated semantics models unbounded K integers consistently with Python's
unbounded integers, stable list order, and duplicates. It does not model
floating-point numbers, other terminating ordered numeric objects, overloaded
comparisons, comparison side effects/exceptions, or general Python module
behavior.

## 7. Proven versus assumed accounting

### What is machine-proven

Conditional on the submitted K definition and K toolchain, the fresh
reachability proof establishes:

> For every finite free list of K mathematical integers `INPUT`, executing the
> exact trusted-regenerated `get_positive` constructor term in the candidate
> harness reaches `filterGt(INPUT,0)`, where the submitted equations recursively
> retain exactly those integer elements greater than zero in original order.

It also establishes the three one-step symbolic cases and four ground boundary
and example cases. The theorem is unrestricted in integer-list length; it is
not finite unrolling or example-only reasoning. The false result and changed

### Gate accounting and decision

- Real-program soundness/non-vacuity on the formal integer domain: **pass**.
  The exact term executes, values are constrained, local equations are sound,
  continuations are preserved, and both sensitivity tests discriminate.
- Source-intent adequacy: **fail**. `PyList ::= nil | cons(Int,PyList)`
  materially narrows “positive numbers in the list” to integers. The concrete
  float witness terminates in both trusted and submitted Python but is excluded
  from every K entry precondition.
- Evidence/trust auditability: the commands, scripts, statuses, finite samples,
  and informal generated-semantics bridge are explicitly preserved. Testing is
  not treated as a substitute for the K theorem.

The restricted integer theorem is genuine partial progress, but it is not a
legitimate proof of the full HumanEval source contract. Per the benchmark's
specific decision rule, the material domain narrowing is `FAIL / NOT_LEGIT`,
not a non-fatal concern.
