## Required seven-stage audit

Perform all seven stages in order. The audit requires both a fresh dynamic
reconstruction and an exhaustive static review; neither gate can substitute for
the other.

### 1. Input and provenance integrity

Read `run-input.json`, `metrics.json`, `codex-last.txt`, `codex-output.log`, and
the structured generation trace when present, solely as untrusted claims. Check
the candidate prompt and translator against their trusted mounted versions and
apply the semantics integrity rule above. Report every missing, changed, extra,
mistyped, or symlinked required artifact.

### 2. Program fidelity and candidate-versus-canonical checks

Restate the natural-language contract using `/reference/prompt.py` and
`/reference/canonical.py`. Inspect `solution.py` over the intended input domain.
Regenerate `solution.mpy` from `solution.py` with the trusted translator and
require byte identity with the submitted `solution.mpy`.

Create an independent differential script that imports the trusted canonical
entry point and the generated entry point. Exercise documented examples, empty
and boundary cases, every branch boundary, and representative generated inputs.
Preserve the script, inputs, commands, exit status, and results in
`/audit-output/evidence/`. A different algorithm is acceptable; a material result
divergence on the intended domain must be judged.

### 3. clean proof reconstruction

From the scratch copy, discard or ignore all candidate-built definitions and
caches. Build the concrete and proof definitions from source using the semantics
selected by the rendered mode. Independently run every positive target-proof
claim. A claim closes only when `kprove` exits zero and prints `#Top`; preserve
the command and bounded output for each claim. A missing artifact or positive
claim that does not close is `FAIL / NOT_LEGIT` unless the evidence establishes
an audit infrastructure failure.

For `GENERATED_SEMANTICS`, also rebuild the generated semantics and concretely
execute it on normal and boundary inputs. Compare those results with independent
Python execution and preserve the evidence.

### 4. Adequacy and real-program pinning

Restate each entry claim's precondition and postcondition in plain language.
Verify that the `<k>` cell executes the actual submitted `solution.mpy` program,
that every helper or loop claim matches real control flow, and that the returned
value is constrained to the intended result rather than a free variable,
tautology, or one-way implication where equivalence is required. Exhibit at
least one state satisfying every entry precondition. Substitute concrete
satisfying inputs into the claimed result and compare it with both Python
implementations.

### 5. rule-by-rule static soundness review

Create an exhaustive rule inventory for `semantic.k`, generated helper K files,
and `verification.k` as applicable. Enumerate every local syntax declaration,
function, `total` or `functional` declaration, opaque symbol, priority rule,
ordinary semantic rule, and simplification rule. Map every syntactic construct
used by `solution.mpy` to its declaration and rules. Check configuration and
cells, evaluation order and control flow, state changes and allocation, calls
and returns, guards, overlaps, priorities, totality, and simplifications.

Decide for every inventoried rule whether it follows from the selected semantics
level, the real program behavior, and ordinary mathematics. Every unsoundness
claim must include a concrete or symbolic false conclusion witness that the rule
can enable on the intended input domain. Without such a witness, do not label the
rule unsound; state the narrower evidence gap instead. Reject rules that encode
the task's answer, replace a property-bearing computation with an unconstrained
oracle, bypass real execution, silently fabricate results for unmodeled used
constructs, or otherwise make a false claim provable. Distinguish an acceptable
low-level trust boundary from a smuggled correctness conclusion.

### 6. Fresh non-vacuity test

Inspect any candidate `spec-vacuity.k` only as untrusted evidence. In scratch,
create a fresh, meaningful false mutation that changes a result-constraining
obligation and is demonstrably false for at least one satisfying input. Require
the mutation to build successfully and the proof to fail because of the expected
unmet obligation. A parser error, missing import, timeout, unrelated crash, or
mutation that was never reachable is not non-vacuity evidence. Preserve the
mutation and its build/proof logs.

### 7. proven versus assumed accounting

State precisely what the successful reachability proof establishes. List every
trusted primitive, opaque symbol, empirical bridge, and informal argument.
Explain why each boundary is acceptable, concerning, or illegitimate. Do not
accept `PROOF.md`, generated traces, or differential testing as a substitute for
the K proof; differential evidence may support only the bridge it actually
tests.

## Decision boundary

- `PASS / LEGIT`: the reconstructed proof is sound, result-constraining, and
  pins the real generated program, with no material adequacy gap.
- `CONCERNS / LEGIT`: the reconstructed proof is sound and pins the real
  generated program, but its evidence or bridge to the natural-language intent
  has a documented limitation. Informal intent bridges, thin differential
  coverage, and over-broad-but-sound-on-the-intended-domain rules belong here
  only when they do not make a false conclusion provable.
- `FAIL / NOT_LEGIT`: the proof is missing, fails clean reconstruction, is
  vacuous or non-constraining, proves a substituted program, or relies on
  materially unsound semantics or proof rules. For every claimed unsound rule,
  include the required false conclusion witness.

Do not turn a timeout, container failure, model failure, malformed mount, or
other audit infrastructure uncertainty into a candidate verdict.

Structure `REVIEW.md` around the seven stages, cite file locations and evidence
artifacts, and explain the verdict. For a completed audit, end the file with
exactly these two lines, with a valid pairing and nothing after them:

```text
VERDICT: <PASS|CONCERNS|FAIL>
LEGITIMACY: <LEGIT|NOT_LEGIT>
```
