# Independent adversarial review: 123-get-odd-collatz

## Conclusion

The candidate contains a legitimate partial-correctness proof of the submitted
program. I rebuilt both definitions from source, obtained fresh `#Top` results
for the focused loop claim and the complete specification, mechanically pinned
the entry claim to the trusted regeneration of `solution.mpy`, reviewed every
proof-local rule, and rejected a fresh false-result mutation for the expected
semantic reason.

I assign `CONCERNS / LEGIT`, not `PASS`, for two non-fatal limitations:

1. The human-facing assertion that the returned sequence is an ascending
   permutation rests on the supplied `sortVS` primitive. The K theorem
   constrains the actual heap to `sortVS(...)`, but it does not prove an
   `isSorted`/permutation theorem. The concrete supplied equations and
   differential tests support this boundary only finitely.
2. `canonical.py` uses floating `/` for an even Collatz step. On five large
   positive inputs in the independent test set it either loses integer
   precision or raises `OverflowError`, whereas the generated `//` program
   agrees with the prompt's exact-integer Collatz definition. This is a
   canonical-implementation/source-contract discrepancy, not a substitution or
   domain restriction in the generated proof.

Neither issue permits a false proof-local conclusion or narrows the formal
domain. The formal precondition remains every K integer `N > 0`.

## 2. Program fidelity and candidate-versus-canonical checks

### Source contract

For a positive integer `n`, start the Collatz sequence at `n`, repeatedly use
`n/2` when even and `3*n+1` when odd, stop at `1`, retain exactly the odd
sequence values, and return them in increasing order. `n = 1` returns `[1]`;
the documented example is `get_odd_collatz(5) == [1, 5]`.

This is naturally a partial-correctness contract here: the requested proof
need not prove the Collatz conjecture. It must show that any terminating
execution produces the requested list.

### Submitted implementation

`/candidate/solution.py` implements the exact integer transition with `//`.
It keeps two additional local values, `start` and a complete `trace`, to expose
a finite execution witness to K. These locals are not returned and do not
change the function signature. The `odds` list receives each odd value greater
than one when its odd branch runs; terminal `1` is appended after the loop; the
list is sorted in place and returned.

I regenerated the constructor program with the trusted command:

```text
python3 /reference/py2mpy.py /candidate/solution.py \
  > /tmp/audit-work/candidate/solution.regenerated.mpy
```

It exited 0. `cmp` exited 0, and both submitted and regenerated files have
SHA-256
`de340c95772848f976baf13056614c5e1f702f3c85e5b3e18efdf3bc07186c7c`.
See [03_fidelity.log](evidence/03_fidelity.log).

### Independent differential

[03_differential.py](evidence/03_differential.py) imports the trusted
canonical and generated entry points by absolute path and uses a separately
written exact-integer Collatz oracle. Its 509 intended-domain inputs contain:

- the documented example;
- `1..300`, covering loop exit/entry and both parity branches;
- 200 deterministic generated inputs in `1..1,000,000`;
- boundaries around `2**53`, `2**63`, and large powers of two.

Results:

```text

candidate_vs_contract_mismatches=0
canonical_vs_contract_mismatches=5

```

For example, on `18014398509481986 = 2*(2**53+1)`, canonical floating division
rounds the next odd integer and returns `[1]`; the generated program and exact

`2**2048`, canonical execution raises `OverflowError`, while the generated
program and exact oracle return `[1]`. The complete reproducible inputs are in
[03_inputs.txt](evidence/03_inputs.txt).

The prompt's domain is positive integers without a floating-size bound, and
its Collatz transition is an integer transition. I therefore judge the
generated use of `//` to satisfy the natural-language contract; I do not
reinterpret the canonical's float artifacts as required behavior. The
disagreement remains a material provenance concern and is reported rather
than hidden. Probes `0` and `-1` also diverge, but both are explicitly outside
the source and formal domains. There is no “empty” value in the positive
integer input type.

**Stage 2 result: PASS for source-contract fidelity, with the documented
canonical discrepancy contributing to `CONCERNS`.**

### `sortVS` boundary

`sortVS` is declared by the supplied semantics as
`[function,total,symbol(sortVS),no-evaluators]`, with concrete insertion-sort

bypass program-defined code: `.sort()` is itself the fixed external operation

What is missing is a mounted, machine-checked theorem that `sortVS` is an
ascending permutation for every integer sequence. I therefore do **not**
label the supplied rule unsound and do not invent a false-rule witness. The
narrower evidence gap is that the human-facing ordering bridge is a named
trusted primitive supported by concrete equations and finite differential
tests. This is acceptable for legitimacy but prevents an unqualified `PASS`.

## 7. Proven versus assumed accounting

### What the K proof establishes

Under the supplied `MPY` semantics, for every K integer `N > 0`, every
terminating execution of the exact submitted `get_odd_collatz(N)`:

- returns reference 0 without exception;
- allocates the returned `odds` list and internal `trace` list as specified;
- leaves an actual finite trace beginning at `N`, ending at `1`, and obeying
  the exact even/odd Collatz transition at every adjacent pair; and
- leaves the returned heap list equal to the supplied `sortVS` applied to
  exactly the odd trace values, including terminal `1`.

The theorem is result-constraining, body-sensitive, non-vacuous, and covers
the entire positive-K-integer source domain. It does **not** prove that every
positive integer terminates; that would include the Collatz conjecture and is
outside partial correctness.
