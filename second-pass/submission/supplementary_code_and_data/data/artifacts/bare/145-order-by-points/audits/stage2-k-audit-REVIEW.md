# Independent adversarial audit: 145-order-by-points

## Executive finding

The candidate's source implementation appears extensionally correct, its submitted
`solution.mpy` is byte-identical to trusted regeneration, its generated K
definitions rebuild cleanly, and all 13 submitted positive claims independently
close with exit 0 and `#Top`.

Those facts do not amount to the requested unrestricted partial-correctness
theorem. The only symbolic claim about executing the submitted function stops at
`ListVal(sortWith(VS, PointKey, solutionDefs))`. The claims connecting
`sortWith` to the declarative `specSort` cover only the empty and singleton
lists; the two insertion claims cover insertion into an exactly singleton tail.
All remaining sorting results are fixed examples. There is no claim for
arbitrary finite integer lists, no induction/circularity over arbitrary `Vals`,
and no universal orderedness/permutation/stability result. A fresh claim for the
missing all-lists relation gets stuck.

This is a material narrowing of the HumanEval source-contract domain. Under the
benchmark-specific decision boundary it is not a legitimate proof, even though
the narrower submitted claims are reproducible and non-vacuous.

## 2. Program fidelity and candidate-versus-canonical checks

### Source contract and implementation

The trusted prompt requires `order_by_points(nums)` to accept an unrestricted
finite list of integers, sort it by ascending signed digit sum, and preserve
original order when scores tie. For a negative integer the canonical helper
negates the integer, makes the first decimal digit negative, and sums the
digits. Thus, writing `d(n)` for the ordinary digit sum of `abs(n)` and `l(n)`
for its leading digit, the canonical score is:

- `d(n)` when `n >= 0`;
- `d(abs(n)) - 2*l(abs(n))` when `n < 0`.

The candidate implements exactly that formula as a lambda passed to Python's
stable `sorted`. It handles zero, positive and negative single-digit values,
multi-digit values, duplicates, equal-score values, and arbitrary-size Python
integers.

### Trusted regeneration

The exact reconstruction commands are in
`evidence/run_stage2.sh` and their output in
`evidence/stage2-fidelity-differential.log`. The central commands were:


Both exited 0. Both files have SHA-256
`74c6b868e58611b8799447498c1ad9182b0ab1569f6a477546e42ab920771141`.
This establishes byte identity with trusted regeneration.

### Fatal adequacy gap

The claims do not compose into an unrestricted sorting theorem:

1. c05 ends at `sortWith(VS,...)`; it does not constrain that value to
   `specSort(VS)`, orderedness, a permutation, or stable tie order.
2. c06 and c07 prove the `sortWith/specSort` relation only for lengths 0 and 1.
3. c08 and c09 fix the tail to `.Vals`; they prove insertion only into a
   singleton list, not an arbitrary already-sorted tail.
4. c10-c12 are three fixed executions (lengths 5, 0, and 4).
5. c13 checks orderedness for one fixed output only.
6. There is no recursive reachability claim or circularity over `VS`, no
   permutation theorem, and no universal stability theorem.

The missing natural relation was tested in
`evidence/adequacy-probe.k`:

```k
claim
  <k> sortWith(VS:Vals, PointKey, solutionDefs) => specSort(VS) </k>
  ...
```

It parsed and executed against the clean definition but exited 1 with
`WarnStuckClaimState` on symbolic `VS`; see
`evidence/stage4-adequacy-pinning.log`. Failure of this reviewer-authored
claim is not itself a defect—the candidate was never required to use that
exact proof architecture—but it confirms the static fact that the submitted
claim set supplies no arbitrary-list induction/circularity.

The source contract is unrestricted over finite integer lists. Empty,
singleton, and finitely many fixed examples materially narrow that domain.

### Result-bearing lambda bridge

S12 does not construct a closure and later execute the lambda body for each
element. It recognizes the complete submitted body and returns `PointKey`; S36
then supplies `pointScore`. As a result, the concrete and symbolic sorting
executions do not traverse the otherwise-present `abs`/`str`/`map`/`int`/`sum`,
conditional, comparison, and subscript rules for each key.

This bridge is:

- exact in syntax and body-sensitive (the `2` to `3` mutation is rejected);
- value-constrained by complete `pointScore` equations;
- informally justified by the elementary signed-digit derivation;
- empirically supported by the K/Python runs and 5,013 Python differential
  cases.

But the candidate contains no bridge-free universal K theorem that evaluating
the actual program-defined lambda body at arbitrary `N` yields exactly
`pointScore(N)`. The spec then uses that same `pointScore` in `specSort` and
`isOrdered`, so occurrence of the same symbol on execution and specification
sides is not an independent connection proof. This is a material validation
and trust-boundary limitation under the Kit proof-extension contract. It is not
needed to establish the final failure: even provisionally granting the bridge,
the submitted claims still lack the arbitrary-list theorem.

## 7. Proven versus assumed accounting

### Precisely established by the reconstructed K proof

Under the candidate's generated semantics and verification equations:

- four fixed score computations have the stated values;
- for any symbolic `VS:Vals`, invoking the exact closed submitted body reduces
  to the internal `sortWith(VS,PointKey,solutionDefs)` term;
- executable and declarative sorts agree for empty and singleton integer-value
  lists;
- executable and declarative insertion agree for inserting one integer into an
  exactly singleton list under either score comparison;
- the three fixed entry executions have their displayed results;
- one fixed five-element result is nondecreasing by `pointScore`.

That is the complete reachability result. It does **not** establish:

- correctness for every finite integer list;
- `sortWith(VS)=specSort(VS)` for arbitrary `VS`;
- universal orderedness, permutation preservation, or stable tie ordering of
  the submitted function's output;
- a machine-checked connection from actual lambda-body execution to
  `pointScore`;
- total correctness/termination (the requested theorem is partial correctness).
